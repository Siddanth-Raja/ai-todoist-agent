## 3. Primary Oracle topology, fallback and request flow

### Concrete eligible candidate

Start with **one Always Free-eligible Ubuntu ARM64 VM.Standard.A1.Flex, 1 OCPU / 6 GB RAM**, a 50 GB boot volume and a separate 50 GB data volume in the tenancy's home region. Use systemd, a production Next.js build, loopback reverse proxy and **one** Uvicorn worker. Mount the data volume at `/var/lib/pcos`; fail startup if its environment marker/mount is missing. This is a normal VM-attached block filesystem, not a network file share or serverless filesystem. Never multi-attach the data volume or run active replicas.

The repository's Next.js lockfile includes Linux ARM64 SWC/sharp packages; Python uses ordinary FastAPI/uvicorn and SQLite. This supports an ARM64 feasibility inference, not a successful install/build claim. Six GB provides a plausible small single-user runtime/build envelope, but memory peaks, native wheels and restart behavior must be measured. Keep the backend dependencies reviewed/pinned in later implementation; do not install or alter them now. The tiny free E2.1.Micro (1 GB RAM/fractional CPU) is not a proven substitute for the combined app.

Reserve a second **1 OCPU / 6 GB** VM with its own 50 GB boot + 50 GB data only for separately authorized synthetic staging. Two such VMs running all 744 hours of a 31-day month consume **1,488 OCPU-hours and 8,928 GB-hours**, within the documented 1,500/9,000 allowance, and exactly 200 GB combined volumes. One uses half those amounts. All tenancy resources count: this leaves no volume room for a third recovery VM. Test recovery sequentially using isolated directories on an existing synthetic VM or release synthetic resources first; never borrow a personal disk or exceed limits. No paid performance tier, automatic disk growth or extra trial-credit instance.

Oracle currently documents 200 GB combined boot/block storage and five volume backups; the design relies on application backups, not scheduled volume snapshots. Console eligibility and selected volume performance must be verified before creation, and a nonzero billable line is a stop condition. The platform capacity may not exist in the selected home region. [Always Free limits](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm).

Avoid paid NAT, load balancer, DNS zone, purchased domain, public tunnels and optional observability services. Verify the exact address/gateway SKU is zero-cost in the chosen tenancy before provisioning; do not infer that from a generic free-VM label. [Networking prices](https://www.oracle.com/cloud/networking/virtual-cloud-network/pricing/), [public-IP behavior](https://docs.oracle.com/en-us/iaas/Content/Network/Tasks/managingpublicIPs.htm).

Tailscale Personal/Serve supplies a private HTTPS hostname with no purchased domain. Restrict the tailnet to the owner and explicitly enrolled nodes, with distinct production/staging grants; no device sharing, Funnel or public application ingress. Certificate hostname and connection metadata are not College content; use opaque hostnames. [Tailscale pricing](https://tailscale.com/pricing), [Serve](https://tailscale.com/docs/features/tailscale-serve).

### Capture and read flow

1. Authenticate and resolve principal, workspace, allowed course/section set and operation permissions on the server. Resolve reviewed course bindings from SID-151; client conversation IDs remain hints unless attested by the platform. Never infer another transcript's contents.
2. Read existing context/revisions and valid consent. Accept only the current reviewed Calc, ENGR Topic 4 and derivatives language families; unmatched consequential wording stays saved for review. Both surfaces use the same adapter.
3. Dispatch the exact command/key/payload through the single write boundary. Existing domain transactions commit events, changes, version and durable receipt together. Acknowledgment follows commit.
4. On a lost response, look up the same command before an exact retry. Preserve changed-payload rejection, field-level conflicts and canonical-version readback. Do not promise at-least-version through an unsupported new query parameter: the client checks returned versions and retries a read if needed.
5. Both connected conversations and the app read the shared result. A new capture invalidates an old judgment; assessment is a separate explicit command. Mere state/status reads never run assessments, cleanup, provider refreshes or cursor advancement.

## 4. Authentication and ChatGPT are separate layers

### Own-device browser/app baseline

Tailscale authenticates and restricts the network path; the application still authenticates the owner. Select a local single-owner login and server-side sessions, avoiding a required hosted identity subscription. Future implementation uses a mature password-hashing library (Argon2id), a strong owner password enrolled through the trusted administrative path, rate-limited login, no public signup/reset-email dependency, and hashed opaque sessions in the same SQLite database. Password reset requires authenticated owner recovery through that administrative path and invalidates sessions. This is a small app login, not a new OAuth authorization server.

An immutable server-created account ID maps to exactly one enrolled actor/workspace and allowed course/operation set. Never accept identity from request bodies, email suffixes, arbitrary proxy headers or a Tailscale display name. Tailscale Serve strips its own identity headers, but loopback callers can bypass that proxy; headers alone are insufficient app authorization. Protect the runtime OS account and service files; neither VM root nor a compromised Mac administrator is outside the trust boundary. [Serve identity boundary](https://tailscale.com/docs/features/tailscale-serve#identity-headers).

Use host-only Secure/HttpOnly/SameSite cookies, CSRF + exact Origin checks for mutations, 12-hour idle/seven-day absolute session limits, and explicit renewal/logout commands. Read/status must not update session timestamps. Check account/session revocation on every request. Deny direct LAN access and cross-origin calls; no static backend key in browser storage or bundles. Legacy server-only compatibility credentials stay behind an authenticated route/method allowlist, never a general forwarding proxy.

Revoking a PCOS session/account, removing a lost device from Tailscale and revoking capture consent are separate controls. A revoked session cannot be revived by a still-valid VPN device. Logout clears local sensitive caches; use `private, no-store` responses. Keep retry journals bound to environment/actor/workspace/auth generation, maximum seven days, status-before-exact-retry, and clear them on logout/environment change. Offline drafts are not acknowledged server captures; no automatic replay after restore.

On Oracle, use restrictive service-owned secret files or systemd credentials on the encrypted volume, outside source/build/logs; enroll/rotate through private administration and keep an independent recovery copy. Use distinct OS identities for frontend and Python when enforcing file access. OCI IAM authenticates infrastructure administration, not PCOS users. Do not require a Mac or interactive SSH session for normal VM boot; prove unattended service restart. On Mac fallback, use Keychain/restricted files and acknowledge the post-reboot login/unlock dependency. Only Python gets backend/provider secrets; no `NEXT_PUBLIC_*` secrets. Database fingerprint keys survive restarts and follow a versioned migration. Backup recovery keys must be accessible independently of both failed host and Oracle account. Block volumes are encrypted at rest by default; this does not protect data from a compromised live VM. [Block encryption](https://docs.oracle.com/en-us/iaas/Content/Security/Reference/blockstorage_security.htm).

### ChatGPT/MCP: conditional, not included in the browser promise

A Tailscale-only URL is not reachable by ChatGPT's service. Do not expose either host publicly to fix this. The candidate path is OpenAI Secure MCP Tunnel, with its outbound client and private MCP adapter on the Oracle VM (on the awake Mac only for fallback). It requires the correct Platform organization/workspace association and tunnel permissions. Tunnel connectivity is not end-user authorization. OAuth discovery can traverse it, but the authorization server is not automatically tunneled. [Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels).

For that optional path, prefer an independently reachable Auth0 Free OAuth issuer rather than writing a local OAuth server. It is not required by the browser baseline. Auth0 currently lists Free at $0/month for up to 25,000 monthly active users, with no card needed to sign up. Use default issuer domains and Free features only, not trial-only entitlements; no custom-domain/card or paid environment feature is assumed. Enrollment, exact resource limits, callbacks, tunnel entitlement and absence of new charges must be verified before any later activation. The tunnel guide does not establish a universal zero-charge entitlement; do not count an unverified tunnel as a guaranteed $0 feature. No API-funded model fallback or subscription upgrade is authorized. [Auth0 pricing](https://auth0.com/pricing).

Preserve the required MCP auth design: protected-resource/authorization-server discovery, authorization-code PKCE S256, exact callback, resource/audience validation, approved issuer/signature/client/expiry and operation scopes. Explicitly enroll `(issuer, subject, client)` to the same existing PCOS actor/workspace as the browser; never create a second fact store. Local grant revocation/authorization epoch rejects valid-but-revoked tokens on every request. Start with `college:read`/`college:status`; capture/assessment/review are separate permissions and capture additionally needs SID-151 opt-in. No token passthrough to providers; no client-credentials grant for personal facts. [OpenAI authentication](https://developers.openai.com/plugins/build/auth).

Current Help Center documentation lists MCP apps as web-only, Pro read/fetch support, and full write/modify MCP for Business/Enterprise/Edu. The developer connection guide establishes a private tunnel testing path, not entitlement for every plan/client. Therefore **ChatGPT mobile capture, write-capable access on the user's current account, and two-conversation write continuity cannot yet be promised**. Recheck the exact account and selected client with synthetic data only after authorization; existing canary evidence does not satisfy this gate. If unsupported at no new charge, leave the integration unavailable; app capture remains usable. [Plan/client limits](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt), [connection testing](https://developers.openai.com/plugins/deploy/connect-chatgpt).

Calendar-enabled personal production still requires SID-131 and separately authorized provider setup; every external action retains its approval gate. Use the eventual chosen secure callback and encrypted per-provider credentials. Blinn remains pending administrator approval with unknown freshness and null check times. Do not mount legacy model/provider routes simply because the network is private.

## 5. Storage ownership and concurrency

Set **only** `APP_DB_PATH=/var/lib/pcos/pcos.sqlite3` on the Oracle data mount (an absolute private Application Support/PCOS path for Mac fallback); reject conflicting `APP_DATABASE_PATH`, `:memory:`, relative paths and missing volume/environment markers in the installed runtime. Use an environment UUID marker and schema manifest to prevent booting a staging image against production data. One Python process owns database access; obtain a lifetime OS lock on the volume to reject a second owner. Node/proxy do not access it. No horizontal replicas, autoscaling or hot second writer. Before moving a surviving volume, stop/fence the old VM and verify exclusive attachment; a process lock alone does not fence a second VM. Rotate browser/OAuth/backup credentials independently; database fingerprint keys are durable data dependencies, so rotation requires a versioned migration preserving old receipt/tombstone verification, never regeneration on each deploy.

Retain DELETE journaling, `secure_delete=ON`, `temp_store=MEMORY`, foreign keys, per-operation connections and transactions; require `synchronous=FULL` on writers. Do not enable WAL, Litestream/WAL replication, shared network SQLite, serverless `/tmp`, or database copying as a live replica. SID-151's guard makes this a correctness/privacy requirement, not an optimization preference.

One worker still has concurrent FastAPI request threads. Add a bounded application write gate for all installed-runtime mutating paths, including consent, capture, lifecycle, sessions, migrations and maintenance. Enforce a 128 KiB transport-body limit, existing tighter domain-field limits, bounded MCP sessions and per-principal request rates. Default queue capacity 16; reject overload before acceptance with 429/Retry-After. Preserve SQLite's five-second lock bound, short bounded read snapshots and atomic expected-revision checks. Never hold a SQL transaction while awaiting an identity service, providers or backup storage. If a network timeout masks commit, report uncertainty/status lookup, not a new command. A process lock is not a substitute for SQLite transactions or field revisions.

Read operations use short `mode=ro` snapshots; no audit last-access writes, session renewals, cleanup, initialization or work dispatch inside the two College read tools. Pause retention maintenance during byte-stability tests to distinguish independent maintenance from read side effects. An explicit brief/open action may issue `request_assessment` after a stale read; keep that as a separate visible command.

Capacity assumption: one user, 1–5 active devices/conversations, under 10,000 bounded reads and 1,000 writes/day, database initially under 250 MB. These are design targets, not measurements. Stage at ten concurrent readers and two racing writers; target bounded reads under two seconds and ordinary local capture/assessment under five seconds absent provider calls. Alert at 70% disk or persistent memory pressure; reserve room for database, journal and one backup copy. Default metadata limits remain in force.

Reconsider storage only after measured lock timeouts above 1% under ordinary single-user load, multi-user authorization requirements, sustained writes that exceed the bounded gate, or a real need for regional redundancy. A future PostgreSQL migration is a separate contract/privacy/transaction review with an explicit cutover, not an automatic scaling switch.

## 6. Assessment, restart and maintenance

Use synchronous bounded local assessment through `CollegeDomainService.request_assessment` initially. Do not introduce a general job queue. Its queued/running states remain durable receipt states visible during interruption; the process owns one assessment at a time through the write gate. Build the reviewed cross-course baseline, material coverage, horizon, timezone and SID-151 snapshot from authorized retained inputs in the shared boundary. Both app and MCP use that same input assembler. No provider refresh or model call is part of assessment. Missing stored evidence yields qualified/unknown results, never invented coverage.

This input wiring is an explicit SID-157 gap: the current capture assessment adapter does not supply the context snapshot, and a client-submitted baseline is not sufficient evidence. Bind the snapshot once to the original request identity; a retry must not silently hash a new context snapshot under the same key. If inputs changed, retain the old attempt's failed/invalidated status and use a newly authorized assessment request. Receipt storage remains authoritative; any small runtime request metadata belongs in the same transaction/store and must not duplicate raw content or business logic.

Startup sequence: validate configuration and exclusive volume lock → verify environment/schema/key manifest → perform explicitly permitted migration/bootstrap → run SQLite integrity/foreign-key checks → bounded recovery/privacy maintenance → construct services → enable readiness. Normal restart of an existing deployment never creates a missing database, re-enrolls an owner, grants opt-in, seeds personal course facts or regenerates fingerprint keys.

Before readiness, inspect interrupted assessment records. If no atomic ready projection/applied receipt exists, use the domain's failure transition to mark queued/running attempts `retryable_failure` with a bounded `interrupted` code. Preserve receipt identity/history. Do not recompute on a GET or blindly replay the queue at startup. An authenticated same-payload command can retry through existing transitions; expired horizons require a new explicit request. A committed result with a lost response is simply read back. Unexpected received fact commands also require reconciliation against their stored atomic receipt/event batch; keep visible pending/error if no existing safe transition is available, rather than invent success.

Pending external actions are different: an interrupted `executing` action might already have reached its provider. Preserve/transition to the existing uncertain outcome and block automatic replay/reconfirmation until separately authorized provider reconciliation. SQLite cannot guarantee exactly-once provider effects. Startup has no provider network permission in staging.

Run only narrowly scoped **operational maintenance** in the owning process: raw-expiry cleanup at startup and every 15 minutes, daily backup, session expiry cleanup and health metrics. It uses existing SID-151 lifecycle commands and the same write gate, with no provider or academic monitoring. Time-based read suppression applies at the seven-day boundary even before physical cleanup; missed maintenance while down is caught before readiness. Preserve useful structured claims, question dispositions and learning needs; expiry never means resolved. This infrastructure work is needed for retention and recovery, not SID-149's general background execution.

Future workers must submit commands through the owner or wait for separately reviewed storage/lease support. Provider polling/webhooks later need account-scoped checkpoints, deduplication, bounded retries/backoff, failure coverage, and reconciliation before retrying uncertain effects. They cannot directly share this disk from another service. Notifications, Life Manager, iMessage and general proactive monitoring remain future scope.

## 7. Backups, privacy, recovery and rollback

### Primary: automated off-volume backup with owner oversight

Use **private OCI Standard Object Storage**, not required R2 or another billable backup vendor. Proposed combined production/staging use: eight encrypted 250 MB backups per environment (seven rotating daily plus one pre-migration, each intended to expire within seven days), about 4 GB total; reserve additional space for privacy metadata/manifests and failed uploads. Hold combined Standard storage below **8 GB**, including hidden versions/multipart parts. This fits the more restrictive documented 10 GB Standard allowance during trial/paid status as well as the 20 GB combined allowance on an Always-Free-only account. No archive/IA tier, cross-region replication, bucket versioning or locked retention rules are required. [Object allowance](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm).

Use SQLite's backup API, verify integrity/foreign keys/receipt verifiers, encrypt client-side before upload and authenticate the manifest (environment, schema, build, checksum, privacy generation). Use the reviewed age recipient-encryption tool described below, not custom cryptography; separately authenticate backup manifests. Keep recovery/decryption material outside the VM and Oracle account; never depend only on a cloud-resident key to recover from account loss. OCI also encrypts objects at rest by default. Use instance-principal IAM limited to that environment's backup/suppression objects, no public access or preauthenticated public links; separate retention cleanup permission from ordinary request paths. App privacy authorization is not OCI IAM. [SQLite backup API](https://sqlite.org/backup.html), [Object Storage security](https://docs.oracle.com/en-us/iaas/Content/Security/Reference/objectstorage_security.htm).

Cost and privacy must fit together: after atomic local privacy commits, batch pending non-content generations for off-volume export on a 15-minute schedule when needed, with no more than one ordinary batch per environment per interval, outside SQL transactions. This deliberately leaves a normal pre-export vulnerability window as well as outage windows; local success is not off-volume durability. At two environments, 96 batches/day × 31 days × three object requests is **17,856 requests/month** before backup/cleanup overhead, below the documented 50,000 allowance. Target fewer than 25,000 combined requests, account for retries/listing/HEAD/failed requests and all other tenancy consumers, and stop backup-sync retries before a conservative 40,000 budget. Back off rather than loop. That stop leaves local privacy working and off-volume sanitation pending; it does not weaken restore refusal. A burst must fit batch/object/metadata size limits; capacity exhaustion must be visible, never silently drop suppression. Use conditional object generations and readback to reject gaps/stale writers. These numbers are a future measured workload budget, not evidence of platform-enforced spend caps.

The owner remains responsible for patching, reviewing backup failures/age and quota use, retaining keys, pruning actual objects and periodically doing isolated restore drills. The VM can back up while the Mac sleeps. OCI copies survive some VM failures but share its account/region failure domain. The selected off-account destination is the existing Mac, specified below; no new storage subscription or hardware purchase is assumed.

### Copy, rotation and offline behavior

The future Mac helper **pulls** encrypted artifacts over authenticated HTTPS using environment-specific, read/list-only OCI access; it cannot delete cloud backups or alter the app. No inbound port, public Mac endpoint, always-awake setting or standing cloud-to-Mac filesystem access is needed. Metadata polling/downloads share the section 7 object-request budget; check once on login/wake with a cooldown and at most once per awake day for the normal copy. This is narrowly scoped backup maintenance, not general proactive monitoring; no helper or schedule is installed now.

Keep **at most seven daily snapshots plus one pre-migration snapshot per environment**, each expiring seven days from its original creation, not download time. No monthly/indefinite archive. A newly connected Mac downloads the latest verified eligible snapshot plus the complete available suppression chain/manifests needed by retained copies; it need not backfill every missed day. Verify pinned source-signature/manifest, environment, checksum, size and privacy generation before atomic promotion of a `.partial` transfer to a durable copy. A checksum proves bytes, not suppression completeness or source identity. Interrupted files never count as backups; discard/retry stale partials under the capacity limit. Never overwrite the last valid copy with an incomplete one. Expired copies are still removed under retention even if this leaves no recoverable snapshot; do not extend retention silently for availability.

If the Mac sleeps/offline, Oracle keeps serving and its own backup attempts continue. No independent Mac copy is produced or sanitized during that interval. Track **last successful Mac copy**, **last verified suppression generation**, **pending sanitation** and **last successful restore drill** separately, without content. On reconnect, reconcile available suppression first, prune expired/affected local copies, then obtain/verify a fresh sanitized snapshot. Report the actual gap; no queued acknowledgment or clock tick can claim a missed copy succeeded. Cloud rotation can delete missed snapshots before the Mac returns. Do not lengthen cloud retention to compensate without review.

A Mac that is only a backup destination must never serve its restored database as a second PCOS truth store. If Oracle fails, activating Mac fallback requires explicit cutover, source fencing and the approved restore checks. Once the Mac becomes the active runtime, its same-disk backups cease to be independent of that runtime. With OCI also unavailable, there is no second off-host copy established by this design.

### Encryption keys and restore verification

Select **age recipient encryption** for the backup payload and privacy metadata: generate an environment-specific recovery identity later through an approved local setup; give Oracle only the public recipient. The Mac copies ciphertext and does not need the private identity for routine pulls. Store the private identity in a passphrase-encrypted identity file outside the backup tree; store its unlock secret in the owner's Keychain, with no plaintext key in logs, source, command arguments, environment or backup files. Keep an offline written recovery record of the identity/passphrase in a separate safe location, verified during enrollment, so Oracle-account loss plus Mac loss does not also destroy the only decryption capability. No existing password-manager subscription, spare disk or hardware token is assumed. Never upload the private identity to OCI. Old keys remain recoverable until every copy they protect has expired and actually been removed; rotation requires a versioned manifest and a tested new key. [age documentation](https://github.com/FiloSottile/age).

Use a separate signature/verification mechanism for manifests, pin the verification key during trusted setup, and keep the recovery manifest/verification material with the offline recovery record. Recipient encryption alone does not authenticate who produced an artifact. This does not defend against a compromised live server's signing authority; restore still needs integrity, contract and completeness checks.

Before personal activation, perform an **owner-assisted decrypt/restore from a Mac copy with OCI unreachable**, using the recovery key without cloud login. Repeat after migration/key changes and at least monthly when the Mac is available; missed drills remain overdue. Decrypt only into an isolated encrypted scratch location with provider access and ordinary app ingress disabled; verify SQLite integrity/foreign keys, schema compatibility, receipt/key verifiers, identity/environment, known synthetic versions and consent. Do not decrypt into the live fallback database. Validate the complete suppression interval before reopening any historical state, run current-time expiry, invalidate sessions/grants and require fresh enrollment. Remove scratch artifacts and record content-free evidence of the actual result. FileVault/OS-backup coverage must be checked during later setup; application encryption does not rely on FileVault, and encrypted scratch must not leak plaintext into unmanaged backups. [Apple FileVault guidance](https://support.apple.com/guide/mac-help/protect-data-on-your-mac-with-filevault-mh11785/mac).

### Forgetting and quarantine apply to Mac copies too

A forget/revoke succeeds at the authoritative SQLite commit with its atomic receipt/outbox, even while the Mac is offline. That says nothing about sanitation of the Mac's older ciphertext. On reconnection, apply the verified suppression chain before any restore, discard affected historical payload copies and fetch a fresh sanitized backup rather than treating ciphertext as current state. Keep necessary non-content suppression metadata until **all** corresponding cloud/Mac/other permitted copies are retired; ordinary seven-day snapshot pruning does not prune that history. No raw content belongs in filenames or suppression indexes.

If Oracle data/account is lost before later privacy operations reached the Mac or another independently durable record, the Mac's newest “clean” manifest cannot prove complete history. **Quarantine all potentially affected historical copies; recover into an empty workspace with capture disabled unless completeness can be established.** A successful decrypt or yesterday's restore drill cannot waive this rule. Quarantine retains access restrictions, not permission for indefinite storage; normal expiry still applies. Offline Mac copies, Time Machine/APFS snapshots or synced backups may remain physically present longer, and encryption/deleting a file is not proof of physical erasure. Inventory/exclude unmanaged copies during later setup or explicitly disclose their retention. This preserves the approved combined-failure exception; it does not promise recovery of all acknowledged data.

**No committed RPO or RTO.** The old 24-hour recovery-point objective and four-hour recovery-time target remain withdrawn. RPO measures recoverable data loss; RTO measures time to safe usable service. Eligible backup age, suppression completeness, owner/key availability and replacement VM capacity determine actual outcomes. Record loss and recovery duration separately. Even a fresh daily snapshot cannot reconstruct a later unsynchronized privacy command.

Seven-day live raw suppression stays unchanged. Daily backups with seven-day intended rotation may retain pre-expiry raw text for roughly fourteen days from capture; deletion delays/offline copies can extend that. OCI lifecycle deletion is best effort, not an exact erasure deadline. Verify/prune expired snapshots and multipart leftovers, without pruning necessary suppression records. Do not enable immutable retention that prevents forgetting-related sanitation. Unmanaged volume snapshots, offline browsers and ChatGPT copies are separate residuals; no immediate physical-erasure guarantee. Provider snapshots are not app-consistent backups and never bypass reconciliation. [Lifecycle behavior](https://docs.oracle.com/en-us/iaas/Content/Object/Tasks/usinglifecyclepolicies.htm), [SQLite secure-delete limits](https://sqlite.org/pragma.html#pragma_secure_delete).

**Approved local-first policy:** if authentication and SQLite are available, off-volume backup unavailability (including R2 failure if ever selected) must not prevent local capture-consent revocation, forgetting, or raw removal/expiry. Atomically commit the existing lifecycle changes, dependent retraction/cache-generation invalidation, tombstones, durable receipt and minimal non-content pending suppression/revocation metadata in an outbox in the same database. No backup-storage request belongs inside that transaction. This outbox is future recovery bookkeeping, not a second fact store or implemented capability.

Acknowledge the local outcome after commit, separately from backup sanitation: “Capture disabled” or “Forgotten from active PCOS state”; backup suppression may still be pending. Do not claim deletion of historical backups, cloud snapshots, offline browser data or conversation-host copies, and do not introduce a new College receipt state. If the local transaction fails or its response is lost, report failure/uncertainty and use the original receipt identity for lookup; never claim durable success. When consent storage is untrustworthy, fail closed to new automatic capture.

“Immediate” means effective at local commit. The single-owner write gate must cover consent validation through capture commit and serialize that interval with revocation; queued captures recheck consent. Previously committed captures remain prior state; captures ordered after revocation reject. Forgetting suppresses dependent content from subsequent reads. A same-disk restart recovers the outbox and honors revocations/tombstones even while the backup destination remains unavailable. State/status reads never drain the outbox.

When the off-volume destination becomes available, synchronize contiguous privacy generations idempotently using atomic generation manifests and verified checksums (conditional object-generation checks for OCI Object Storage) and verify their durability before eligible restore reconciliation. Retain only opaque target identifiers, deletion types/times and consent-revocation markers, not text or low-entropy content hashes. Then create a sanitized backup and prune eligible managed copies. Lost upload responses or generation gaps leave historical restoration blocked, without undoing a local privacy command or changing its receipt identity. Suppression records outlive every allowed backup; never prune them merely because raw retention expired.

**Combined-failure exception — off-volume destination unavailable followed by total disk loss before suppression sync:** the old backup and last off-volume fence cannot reveal the newly lost privacy commands. An apparently clean/latest remote generation is not proof that no later revocation or forgetting occurred. Acknowledged local receipts may be lost with the disk. No checksum, encryption or scheduled backup reconstructs information that was never independently preserved.

Every historical restore starts quarantined, without app reads, capture, sessions or provider actions. To reopen historical data, establish complete suppression history through the last period during which privacy commands could be accepted, normally from the surviving original database/outbox or independently durable evidence covering that entire interval. Do not infer completeness from a remote fence, backup timestamp, an old zero-pending count or the user's recollection. A clean checkpoint followed by a new privacy-accepting period is insufficient. Apply suppression through existing lifecycle/dependency logic, run expiry at current time, invalidate derived generations and reset authorization before readiness. Never restore OCI volume snapshots, Time Machine, filesystem snapshots or copied databases directly into service.

**If completeness cannot be established after disk loss, quarantine historical backups and recover into a new empty workspace with capture disabled.** Require fresh authentication enrollment and a new explicit capture opt-in; invalidate old sessions/grants and use a new workspace identity. Do not import old facts, summaries, receipts, seeds or browser retry journals. No “restore anyway” path is allowed. Quarantined artifacts still obey retention/deletion policy; quarantine is not indefinite retention permission.

This approved procedure avoids serving unverified old state; it does not guarantee physical erasure of all copies or recovery of lost suppression history. In this combined failure, historical loss can encompass all PCOS history, and a safe full-data restore may never be possible. There is no fixed recovery-time target and no time pressure authorizes bypassing quarantine; empty-workspace service recovery and any later eligible historical recovery must be reported separately. This tradeoff is approved; historical-copy retention limits remain a separate owner decision.

### Migration and recovery runbook

Future SID-157 adds a checksummed schema ledger and explicit migration runner, not opportunistic initialization during reads. Under exclusive ownership: verify environment/path/keys, back up, test the migration against an isolated copy, then apply before readiness. Keep fresh synthetic bootstrap explicit; never seed a missing personal database on restart.

1. Disable ingress/writes and isolate any surviving original disk. Do not send personal recovery data to synthetic staging.
2. Verify backup environment, encryption key, schema, integrity and complete suppression history. If the latest privacy-accepting interval cannot be covered after disk loss, quarantine historical backups and take the empty-workspace branch above.
3. Apply lifecycle suppression and current-time expiry; reset derived generations, sessions/grants and auth epoch. Re-enrollment is not capture opt-in. Compare restored versions/receipts with known acknowledged versions and report loss.
4. Run safe read/receipt checks, then enable readiness. Do not replay provider actions or browser journals. Record data loss and recovery time separately; empty-workspace return is not historical recovery.
5. Restore-drill evidence must demonstrate both eligible recovery and incomplete-history refusal. Prior code rollback uses a reviewed previous build only if schema-compatible; otherwise forward repair or this controlled restore. Never swap an old database into service as a code rollback.
